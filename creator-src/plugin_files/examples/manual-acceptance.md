# 角色资产插件手动验收样例

## 内部测试会话隔离（0.2.5.1 起）

真实模型验收前先确认运行器使用 `thread/start(ephemeral=true)`，且没有恢复持久 thread 的分支；旧版本对照也先隔离此生命周期并记录补丁。不得为测试另建可见聊天，或以事后删除代替隔离。任务恢复从本地 inputs/answers/previous_output 重建。具体规则与无模型生命周期检查见[内部调用隔离](../references/dispatcher-isolation.md)。

## 0.2.5 人物总控与真实模型验收

这些是待执行的输入、比较方法和通过条件，不表示样例已经通过。结构回归与真实模型理解分别记录，不能用schema校验代替人物设计能力。

### 三个故事样例与两个受控改动

1. **跨场矛盾、弧线与隐藏信息**：提供一个完整短剧本，早场人物自述和他人评价称目标角色冷酷；后场实际行动表明他私下持续帮助同伴；结局揭示被误认的身份，首次出场要求保留误判。关键关系与世界规则放在没有直接写目标姓名的场次。比较来源覆盖、综合人物理解、人物定位、设计意图和首稿，而非只比较六维字段。必须分开评价与行为，解释矛盾与弧线，引用相关场次；不得只检索姓名、把冷酷直接画成尖鼻伤疤，或将后续秘密提前变成外显组织符号。
2. **生活条件反事实**：原文没有脸、发、衣装，只说明日常行动、资源与本人维护体面的习惯。先让总控主动产出一套具体推荐；再沿用该人的脸部身份，仅把恒温室内细作改为经常户外高处作业。比较功能结构、打理/固定、防护、维护和活动余量的实际变化，身份约束须保留。无需每个领域都变；本来适用的结构可保留并解释。只加户外/耐用形容词、或无关脸型身高一起变化均失败。
3. **独立小传、复杂冲突**：只给人物小传和必要世界条件，没有资产表，先请求理解与设计方向。小传含必须保留的身份衣装符号，却与频繁攀爬或狭窄通行冲突，材料取得亦有限制。应能先分析、主动提出一套推荐，识别真实跨专项冲突；冲突涉及当前阶段时独立会诊并形成结构结果，属于后续服饰时登记待深化，不在身份首稿越阶段详设；不能以缺资产表阻断文字分析；无指定阶段默认仅当前identity/头像首稿和关键路由，身体衣装留方向，不要求首稿生产全套JSON，也不能声称已完成正式资产流程。
4. **叙事策略反事实**：复用样例1同一人和身份约束，把首次出场策略从隐藏改为允许直观读到压力或控制感。比较哪些呈现选择改变、哪些身份保留，不能只替换阴险/友善标签；隐藏版不泄密，直观版也不机械采用恶人脸公式。
5. **圈层与经济反例**：复用样例2，改变资源取得与消费选择，同时明确资源紧张者也重视整洁、资源宽裕者也可以朴素。比较取得、修补、材料和自我呈现的具体结果；不得用贫穷推断低颜值、脏污、族群或永久体态。

这组基础故事与受控改动按实际缺陷选择小规模组合，保留能证明因果响应、边界与复杂会诊的真实产物。用同模型、同输入对照当前版与候选版；条件、时间和版本固定，出现不稳定或具体缺陷时再定点复跑，不为了分数重抽。每份只收可读理解与推荐、几条关键人物证据/设计机制、真实知识/执行轨迹。

每个判断写清：需要响应哪个原文条件；哪句理解和哪个可见结构响应它；中间机制是否成立；有没有改变不应改的身份或剧情。评价为可接受、需定点修改或阻断，列实际片段。不要用任意总分或字段覆盖率评美感。记录实际耗时、用户决策轮次和会诊次数，说明额外工作解决了什么；常规任务不应为十三项规划变成十三次会诊。

### 分阶段与CLI门槛

1. 初始化默认phased，旧无字段complete不迁移。context-units列当前全部原文块；context缺块、SHA错或来源换版本应受阻；完整且未决空则系统自动ready，无新增用户审批，interpretation_confirmed:false，人物解释由brief审阅。真实阅读是否理解，仍由上述跨场案例检查。
2. 方向稿包含人物理解与设计意图后才路由；inline/independent规划有具体task，defer和not_needed有理由。首图不要求先填写身体五组比例和全部服饰缝线；身体图前必须补完整并确认。
3. inline保留实际知识路径/SHA、具体规范、采用结果和来源性质；独立会诊保留实际返回提案与SHA。仅填used名称、错角色提案、伪造路径或只抄知识摘要均不算真实执行。defer激活补task与理由，不能偷偷覆盖not_needed。
4. direction_first预览在方向已批、身份冻结后可提交；image_first只在明确先图需求时允许方向与身份冻结未批，但context须ready、项目基准/轻规划仍先批。preview不得作为九宫格锚点或打包。
5. 复用一个真实头像回图测试同图转正：实际review pass、无待采纳新细节、未决清空、用户确认同份设计且SHA不变后，promote-candidate可承接审批而不重新生图。改图、改依据、旧prompt、review不通过或未确认均应拒绝。普通痣雀斑随冻结首稿审阅，有经历含义的新伤疤显式决策。
6. 身份→身体→每状态服饰逐步确认；compile-design-card只合并已批快照，冲突拒绝，审批可追溯继承，不能悄悄新创设计。最终五阶段与状态图片名称、审查、SHA和批准均保留；旧完整卡及旧四阶段回归照常。


## 历史0.2.4.1：五阶段、状态服饰与路由（complete回归）

1. 使用样例资产表初始化新项目，运行 `plan --character-id CHR-001` 和无角色筛选的 `plan`。前者只列该角色任务，后者列全员；角色 `base` 有头像、九宫格、全身三项，资产表每个状态各有服饰与执行两项。批量任务不能跳过逐图批准。
2. 未批准头像时尝试提交九宫格提示词，未批准九宫格时尝试提交全身提示词，未批准全身时尝试提交服饰图，未批准本状态服饰图时尝试提交执行图，均应受阻。九宫格默认 9 个中文标签；16 格须有明确用户选择和依据。
3. 对同一角色两个状态分别批准服饰图和执行图。替换其中一个状态的服饰图，只使该状态执行图失效；更换基础全身图，应使所有状态服饰和执行图失效。旧四阶段项目仍能按原阶段打包。
4. 导入回图后检查文件名以真实资产名、状态名、阶段名开头，含短 SHA；打包清单为 `CharacterAssetPackV2`，包含 base 三张身份图与当前状态两张图及各自审查/批准记录。
5. 世界影响专项仅在有环境暴露或技术使用证据时启用，分别核对外观部位和机制；不能从气候直接造固定族群五官。面部妆容专项区分稳定标记、化妆/面绘和剧情临时状态；无妆、无疤可以是完整决定，任何新增痕迹仍须批准。

从同目录 `sample-screenplay.json` 和 `sample-assets.json` 初始化项目；使用 `$character-assets` 提取第 -1 阶段与全员轻规划，并逐步由操作者批准。样例是**输入材料与检查路径**，没有预先生成或批准任何图片。项目目录另选本地新目录。

## 历史0.2.1定点回归

1. 以宋也“奶油白薄衬衫，领口和肩部结构清楚，布料自然垂落”为输入反例。新重点人形卡必须分别给出脸部比例、发际/发流、体态、皮肤、衬衫领肩袖腰摆/门襟/针脚、材料厚度与垂坠、色块位置和饰品有无理由；十专项各记采纳结果或不启用理由；已用专项指出实际写入的细节字段。具体元素仍须操作者批准后才能进正式卡。
2. `CharacterDesignCardV2.1` 缺任一 `visual_details` 字段或 `specialist_coverage` 项时，CLI 应拒绝；旧 V1/V2 卡仍可读取。新 `CharacterSpecialistProposalV1.1` 少于两条 `design_elements` 应拒绝，旧 V1 提案仍可校验。
3. 头像 `CharacterPromptPackageV1` 默认 `aspect_ratio: "3:4"`，两三条候选每条写“3:4 竖版”；`1:1` 没有明确用户覆盖依据应被拒绝。回图检查实际像素比例与取景安全边界。

## 历史0.2.2定点回归

1. 从同框比较组挑两名五官与身材相近的角色。先写十一专项逐人路由，再实际调用特征聚焦与形体专项。焦点方案应区分主锚点和安静区；不要求自动加痣疤。形体方案应写躯干/腿、臂段/腿段、颅胸盆体块、正侧背与剧本动作；未见视图时测试状态为 `not_tested`。
2. 新重点人形卡用 `CharacterDesignCardV2.2`。used 项须保存原样 V1.1 提案、SHA、被选方案及元素到 `visual_details` 字段的映射。删除提案、改动提案正文、换成其他角色提案、把 route invoke 改 skip、写不存在的 option 或越界元素下标，`submit`/`approve-record` 应拒绝。可运行 `python3 -m unittest discover -s creator-src/tests -v` 查看自动回归。
3. 头像提示词只抽取已批准且头像可见的主锚点；全身和背面图再检查体态与后部轮廓。回图审查分别指出卡片设计过散、提示词遗漏或模型偏移；未见对应视图不得写“通过剪影/背影测试”。
4. 对同一有油亮/脏糊问题的回图，报告应分别指出设计空泛、镜面高光、局部微纹理、材料反光或伪影的实际证据；没有图片只报未验证。修图建议以原批准母图为锚，外部去噪和线稿重建不写成已执行或无损保证。

## 历史0.2.3定点回归：身体比例、全身画幅与模卡基线

1. 用“165cm、48kg、瘦高型；肩线自然、腿修长但可信”作为人形 V2.2 卡的全部比例描述提交，应被拒绝，不能靠字数通过。
2. 在卡中按[身体比例交接样例](body-proportion-contract.md)补 `measurement_frame` 与五组锚点；头身给数值，其余给可定位的骨点关系，写明原文事实与设计选择的区别。卡与全身提示词都不得把示例数值当全剧默认。
3. 新全身提示词若只复述身高体重、没有已批准的头身、肩胯、躯腿关系，应被拒绝；补入设计卡原关系后，验收项仍缺头身或躯腿检查也应被拒绝。旧批准 V2.2 卡和旧全身包保持可读；若要从缺锚点旧卡继续制作新的全身图，先修订设计卡并重新批准。
4. 实际回图按同一测量姿态核对，遮挡或透视妨碍判断时报告未验证，不把文本合同通过说成画面质量通过。自动回归运行 `python3 -m unittest discover -s creator-src/tests -v`。
5. 全身提示词包缺 `aspect_ratio`、填 `3:4` 却无明确用户覆盖依据、每条提示词未写 `9:16`，或验收项未核对 `9:16`，均应拒绝。回图审查按最终图片像素核对 9:16 竖版，以及头、双手、双脚和安全边界；画幅正确但身体比例被拉伸也不能通过。
6. 人形头像做 3:4、以脸为主体的头肩近景，可包含上胸，不要求锁骨以上；若服装不入画用 `face_only`，若上胸入画可直接用白色纯色背心或白色运动背心，不生成裸身躯干。2–3 张候选取景及模式须一致。表情九宫格及 16 格继承头像模式；从 `face_only` 切换背心时记录原因并重审整表，单格衣着漂移则整张表重做并逐格复核。
7. 单独全身图的人形 `reference_attire` 为对应的白色纯色背心＋短裤＋赤脚，或白色运动背心＋黑色运动短裤＋赤脚；每条提示词和验收项都要写出对应组合。用剧情服装、鞋或裸身全身图替代默认组合应列为问题。执行资产表重新以设计卡正式服装、鞋履和饰物出图，不能沿用模卡短裤与赤脚；儿童和不适用衣型的角色按有依据的充分覆盖例外处理。
8. CLI 应拒绝新人形提示词包缺 `reference_attire`、阶段不匹配、从 `face_only` 头像切换到背心表情却无 `reference_attire_basis`、例外无依据或文字描述、提示词或验收项漏写对应着装的情况。旧已批准包继续可读。

每轮都核对 `project.json` 的来源哈希、记录版本、操作者与图片审批。`status` 可查当前有效记录；最终按项目实际四阶段或五阶段链路，所有正式图经过回图审查和操作者批准后运行 `package`；preview不得打包。上述图片的视觉达标情况由操作者手动判断。
