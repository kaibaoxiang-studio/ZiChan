# 头像与服饰执行提示词的硬输出合同

适用：新提交的独立人形头像和逐状态服饰执行图。旧项目已批准的记录保持可读；重新提交提示词时须先把对应身份或服饰状态深化为 `CharacterStageDesignV1.2`。本合同要求与已确认设计等量的**可画信息**，不规定字数，不把宋也婚纱或程婉清头像的具体造型变成其他角色的模板。

## 流程门槛

[苏老太跨项目颗粒度案例](prompt-density-example-su.md)展示同一原始剧本如何分开基础头像与木簪尚未典当的执行状态。它只校准完整度和状态连续性，不作为其他角色的外观模板。

1. 主控从完整剧本、资产状态、已批准方向和图片锚点确定当前角色与状态，先完成专项设计。头像逐一处理脸型、发型、眉、眼、耳、鼻、唇、皮肤、妆容、稳定标记和头耳颈饰的设计或明确留空；服饰状态先做可见需求判断，再完成主衣、重点部件、鞋履、妆发及真正采用的佩戴件。读取 Skill 或知识不等于完成专项；真实结果须回到阶段稿。
2. 角色阶段稿保存 `payload.prompt_detail_contract`，由主控核对每个已选且入画的 item。结构化字段供验收，不能把字段名贴入最终提示词。空类目无需伪造物件；已选择的纹样、头纱、腰扣、耳饰、鞋等不能因为在某格较小就从提示词删除。小到无法识别时回设计阶段调整尺度或分界。
3. 只把获批或明确冻结的预览草案转成提示词。提示词专项逐字保留合同中每条 `cues`，先在对话中展示完整、无部位标题、可复制的 `prompts[].text`；操作者有修订机会后，获授权的预览使用**同一正文**。不能把简版设计摘要、固定版式模板或另写的生图短词冒充最终提示词。
4. `acceptance_checks` 至少逐 item 检查一条可见 cue；生成后仍须实际看图，核正面、45°、无头服饰、背面和身份一致性。机器验证只保证字段与文字覆盖，不宣称视觉通过。设计稿缺信息时退回设计师，不能由提示词专项临时补编。

## 头像正文最低覆盖

正文先给人物、年龄段与完全原创身份，再给单一脸型主类及额—颧—颌—颏的转面与 45° 稳定关系；发型须有主名、长度、发际与分缝、人物自身左右前侧发片、背面发量和有根发流。眉、眼、耳、鼻、唇分别写可画的形状和落点，比例只选有辨识作用且端点清楚的少量。肤色与脸颈上胸连续、哑光/光泽和正常头像尺度的纹理边界明确；不要让全脸毛孔、绒毛、压印纹、无根细丝充当真实感。已设计妆容分别写底妆、眉、眼、颊、唇的颜色、覆盖和边界。稳定标记与头耳颈饰逐件写位置、大小、固定和遮挡；选择留空的决定保留在设计合同，正文只在需要避免误生时简短写明。末尾给 3:4、正面单图、完整头肩上胸、模卡衣着、中性背景和摄影光线。

程婉清头像示例是上述**信息密度与顺序**的验收标尺，不要求其他人是圆角方脸、短波波头、耳钉或裸妆。脸型名称不能替代骨点，发型名称不能替代分缝与左右发片，“五官自然”“真实肤质”不能替代已设计的局部结果。正文不写“脸型：”“发型：”等标题。

## 服饰执行图正文最低覆盖

先给生成任务、参考图各自只锁定的职责、9:16 竖版精确 2×2 四格及四格同人同衣。随后按实际衣层组织，而非按词表目录填空：

- 每件入画主衣给品类与远景廓形、身体起止与少量辨识比例、衣片数量及形状、领肩胸腰下摆的连接、叠压和开合、正面/约45°/背面的连续关系、动作余量。连衣裙仍是一件衣物。
- 重点部件按“轮廓和相对尺度 → 所属衣片和人物自身左右 → 片数、叠压、固定与拆装 → 材质/颜色/纹样载体与疏密 → 各视角和动作结果”完整交代。非重点普通衣物也要可画，不能只给品类与“精致、干练”等形容词。
- 已采用的鞋写鞋头、鞋口/鞋面与固定、鞋跟/鞋底、材质配色和前后同一双；已采用的头耳颈、手腕等物件逐件写形状尺寸、人物自身左右、固定/遮挡、出入场时点。妆、发、皮肤依当前状态写真实可见结果，继承身份骨相。
- 画面最后交代各材料分区的厚薄、透度、垂坠和反射，中性背景与用光、伪影控制；必要禁令精确作用于对应物件，不把局部禁令扩成全身无饰。

宋也 S03 婚纱示例是**结构深度**的验收标尺：主衣、右肩翼、翻页衣片、腰扣、线描纹样、头纱、首饰和婚鞋各有独立可画的连接与跨视角说明。其他状态按真实部件数量与画幅可见性达到同等完整度，不照搬婚纱部件、不强塞饰品，也不规定固定字数。正文不写“款式：”“剪裁：”“材质：”等板块标题。

## 阶段稿中的可核对字段

`CharacterStageDesignV1.2.payload.prompt_detail_contract` 使用 `PromptDetailContractV1`，含 `stage: avatar|execution`、`complexity: ordinary|featured` 和非空 `items[]`。每项有唯一 `id`、`kind`、非空 `source_refs[]`、`cues{维度:可直接进入正文的短句}`。`featured` 用于仪式/重点服装或操作者明确要求物件级细节，须有 `focus_component`；普通状态按实际设计，不强制虚构重点件。

头像必有 `face,hair,brow,eye,ear,nose,lip,skin,framing`；妆容若采用则有 `makeup`，头耳颈有采用物则逐件有 `adornment`。服饰执行图必有 `identity,hair,skin,garment,footwear,framing`；实际采用的妆容、重点件、纹样及饰品分别列 `makeup,focus_component,surface_pattern,adornment`。每类 item 的固定维度由 `scripts/phased_design.py` 校验；所有 cue 须进入每条提示词，验收项须逐 item 至少提到一个 cue。若某类明确无，阶段稿需保留原因，不用空 item 凑数。

## 项目路径与产出对齐

主控先固定用户给定的 `delivery_root`，正式角色工程使用其中明确命名的角色子目录作为 `--project-root`。本项目范例为 `交付根目录/05-角色资产/`；标准剧本和资产表分别从 `01-剧本标准化/`、`03-剧本资产表提取/` 读取。`--project-root` 里的 `project.json` 是唯一正式工程标识，不能把插件源码目录或临时工作目录当交付根目录。

正式阶段稿和提示词包由 CLI 保存到 `05-角色资产/records/stage-design/...` 与 `05-角色资产/records/prompt-package/...`；给人看的提示词副本可放 `05-角色资产/提示词/`，但正文须与包内 `prompts[].text` 逐字相同。图片进入 `05-角色资产/images/...`，审查进入 `05-角色资产/reviews/...`，逐状态正式包进入 `05-角色资产/角色资产包/角色ID_角色名_状态ID/`。测试预览须标未批准，不能混入正式包；任何图片都须记录同一提示词包 SHA。角色阶段图批准后，最终资产表的角色/状态对应单元格使用获批图片，交付到 `交付根目录/08-最终资产表/`。其他项目若已有不同编号目录，以用户指定路径为准，但各阶段的来源、记录、预览、正式包与总表必须有明确且稳定的映射。

## JSON 与人读 TXT 双交付

先保存完整 `CharacterPromptPackageV1` JSON，再由 `scripts/export_prompt_text.py` 导出 UTF-8 TXT。TXT 正文精确等于 JSON 中按顺序取出的 `prompts[].text`，用两个换行连接，文件末尾加一个换行；不插入分析、JSON 字段、部位标题或再写一份简版。操作者复制 TXT 即得到已检查的同一份提示词。

Harness 节点必须交并声明 `prompt-package.json`、`提示词.txt`。只读验收检查二者一致以及真实工程设计合同；节点的通过仅代表本轮文字满足合同，主控随后在正式工程提交，不在隔离节点里越界写项目。正式 CLI 提交验证通过后，把原 JSON 存入 records，把 TXT 导出至工程 `提示词/`，并在记录中保存 `text_path` 与 `text_sha256`。提交返回两者路径/哈希，给操作者优先展示 TXT 下载或打开链接，同时保留 JSON。
