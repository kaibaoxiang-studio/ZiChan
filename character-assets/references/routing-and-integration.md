# v0.2.6.1 需求路由、阶段合同与整合

新项目先看 `plan.asset_mode`：`individual` 执行独立人物分阶段路线；`speaking_extra` 交[群演单图设计师](group-ensemble.md)，每状态仅一张独立 9:16 四格执行图；`ensemble` 由同一设计师每状态交一张完整全身群像图。两条群演路线都跳过头像、九宫格和模卡。下文服饰圣经与四图链路只用于常规 `individual`。

## v0.2.6 服饰路由

人物总控先完成全文理解、人物定位与设计意图；进入服饰阶段必须交 `$character-costume-designer`。它建立穿衣风格圣经，面向每状态调度款式、剪裁、配色、材质四项必做和饰品按需，并把人物弧线与剧情类别转成可画结构。首图后若仅衣装问题，重开对应状态文字快照；若改变共用穿衣规则，重审所有状态。新项目只有每状态一张 9:16 四格执行图，不再排独立服饰设计图。


## 先理解请求和人物

单张或批量先明确角色/状态范围、目标阶段、已有批准物、用户决定和未决关键项。`CharacterAssetRequestV1` 可承接 `project_id`、角色和状态 ID、`mode:single|batch`、目标阶段、已有批准物 SHA、来源引用和画幅/模卡例外。批量仅是多项任务排队，每张图仍单独提示、回图、审查和批准。

人物总控先按 [全文理解方法](director-understanding.md) 阅读并复用全剧上下文，分析言行可靠性、矛盾、关系、弧线与观众信息，形成定位和设计意图；六组观察镜头只用于查漏。先理解人物再决定工作，不能从一组职业阶层字段机械激活十三专项，也不能因原文未写外观而全部跳过。

`python scripts/character_project.py plan --project-root ... [--character-id ...] [--variant-id ...] [--stage ...]` 只读列当前任务与阻断，`--character-id` 可重复；无筛选为全员，不自动生成或批准。

## 主控与专项职责

| 人物问题 | 工作责任 | 需要的结果 |
| --- | --- | --- |
| 全剧因果、人物定位、关系与观众信息 | `character-evidence` 支持来源，`character-design` 统筹 | 读过的上下文、跨场理解、设计意图、推荐方向与关键分歧 |
| 世界、实际环境接触、资源和技术影响 | 世界外貌专项 | 接触/维护机制与可见结构；无接触不臆造痕迹，但仍可提出世界相容的创作选择 |
| 群像近邻、主次和焦点 | 群像审查与特征聚焦 | 共享语言、可见差异、锚点与安静区、尚未验证的视角 |
| 脸、发、皮肤和身体留白 | 对应专项规范 | 结合设计意图的具象推荐；身体到对应阶段给可复核比例和体块 |
| 稳定标记、妆容与临时表面 | 面部装饰专项 | 稳定/施加/临时分层，部位、形态、来源性质、状态和焦点；普通痣雀斑可随首稿审阅 |
| 衣装与饰品 | 款式、剪裁、配色、材料及饰品专项 | 取得与维护、结构连接、前侧背、活动余量和状态；同物件唯一主责 |
| 阶段设计变成单图 | 图像提示词专项 | 当前画幅可见锚点、真实设计依据、参考职责和验收项 |
| 回图偏差或局部缺陷 | 审图，必要时修图 | 实际证据、设计/提示词/模型偏差归因、最小返工和整图复核 |

常规任务由主控加载并执行对应 Skill 规范，记录 inline 成果；复杂冲突真实独立会诊并保存返回物。加载 knowledge/reference 与执行 Skill 分开记录，不把读取名称当成执行。详情见 [专项合同](specialist-contract.md)。现有知识可按问题读全文，不新增知识采集工程。

`DesignDirectionBriefV1.specialist_plan` 覆盖十三项的 `inline|independent|defer|not_needed`，阶段稿的 `specialist_execution` 记录实际工作。active规划须有 task；defer激活补task和activation_reason，执行方式改变须说明，基础身份中 not_needed 的妆、发饰和头耳颈判断不跨剧情状态继承。新 `CharacterStageDesignV1.1(scope:costume)` 可凭当前场次的专项任务与 `state_activation_reason` 激活相应专项，见 [剧情状态需求](scene-styling-needs.md)；其他阶段或旧 V1 的 not_needed 改为执行仍须先修方向。默认一套推荐，重要分歧才备选。原文与用户明确改编决定优先，批准依据决定当前范围；模型创作推荐不能伪装事实，专家不能相互覆盖。冲突由主控合成，影响人物或剧情的选择集中交用户决定。

## 默认阶段与首图快看

新项目默认 `design_progression:phased`，身份→身体→每状态服饰分阶段深化，设计方向先确认；头像可以先 preview，不必等待完整身体和服饰定卡。所有预览须有可追溯冻结依据，通过 [转正门槛](phased-design.md) 后才可同图转正；不能作为下游锚点提前使用。`complete` 保留先整卡批准的方式。

用户明确要求“完整头像从 0 到 1”时，身份阶段按 [人形头像完整覆盖与交接](avatar-identity-granularity.md) 激活脸型与五官、发型、皮肤、稳定标记与妆容、头耳颈饰及特征焦点/群像比较。常规项可由主控同轮 inline 执行，复杂冲突再独立会诊；这里的“完整”指每项有设计或明确留空决定，不强迫每个角色长痣、戴首饰或拥有夸张特征。主控先展示文字提示词；若操作者还明确要求预览图，在文字有机会审阅后调用当前会话可用的图像工具，实际审图并标明候选状态。没有可用工具时交提示词和待生图状态，不声称已经产图。

| 正式顺序 | 阶段 | 资产与固定内容 |
| --- | --- | --- |
| 1 | `avatar` 头像，默认 3:4 | 每角色一张获选身份图；默认一套推荐，重要分歧才增候选；脸、发、稳定标记与气质，不做剧情衣装 |
| 2 | `expression` 九宫格 | 每角色一张 3×3 中文标签，明确要求才16格；同身份和着装模式 |
| 3 | `full_body` 全身，默认9:16 | 每角色一张；身体比例、体块、体态，中性背心短裤赤脚 |
| 4（仅 v2） | `costume_design` 服饰 | 每资产表状态一张，无状态则 base；衣装、鞋履、饰品、批准妆容和关键前侧背结构 |
| 5 | `execution` 执行图 | 每状态一张，使用三张基础身份图与本状态已批准服饰图，核四格和连续性 |

前三阶段归 base，后两阶段归状态。不得凭临时情绪新增状态。示例图仅控制构图和中性衣着，不带入参考人物、妆容或背景。

## 合成、变更与兼容

阶段快照分开身份、身体与状态服饰，`compile-design-card` 机械合成 `CharacterDesignCardV2.5`；跨阶段同字段冲突必须先解决，不能最后一份悄悄覆盖。世界影响、面部表面、身份不变量与变体分别追溯，提示词只取当前可见项。

`anchor_images` 保存当前正式上游图 SHA。头像或九宫格重选重审所有下游，全身重选重审各状态服饰和执行，单状态服饰变化只影响该状态执行。v3 输出 `CharacterAssetPackV3`，v2 历史项目输出 `CharacterAssetPackV2`；两者均保留可读资产命名与正式记录。preview 不打包。

旧项目无 `design_progression` 按 `complete`，旧四阶段维持既有链路，旧批准卡和提案继续有效；不自动迁移、重画或把预览转正。新增总控方法可以用于分析，改变旧批准物仍需明确变更流程。
