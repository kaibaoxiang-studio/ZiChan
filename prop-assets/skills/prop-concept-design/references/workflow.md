# 分阶段工作规则

按需阅读当前节点。本文件规定流程行为；字段与模板见 `output-contracts.md`，不在此重复。

## 批量 Prompt 表优先分支

用户要求从剧本、资产道具表或两者生成Prompt表时，先阅读 [批量表规则](prompt-table.md)。把必要的P0—P3作为内部连续工作，交付整表；不以逐件选方向、上传道具图或调用全部子skill作为前提。默认可提出未确认设计并写出具体词，图像回流与定稿仍需后续实际确认。

## P0 项目约束

只确认会影响本轮工作的事项：

- 设计范围：全部清单、指定条目、单道具还是已有基准续做。
- 视觉风格：用户描述或已有角色/场景定稿；世界观不自动等于成图风格。
- 下游用途：故事版/视频复用、概念提案或明确的3D交接。
- 当前已有物：方向稿、主视觉、派生图、已确认设定和知识目录。
- 出图协作：默认提示词交付+外部回流；用户指定工具时再适配其语言和参考图方式。

知识目录只做与当前任务有关的主题索引。缺少参考时，区分“影响当前设计判断的缺口”和“以后可补的知识”；只有前者需要当轮处理。不得为补齐知识库自动开展具体剧本试跑或外部检索。

涉及时代文化时，按 [时代文化与装备体系专项](era-and-culture-equipment.md) 判断项目采用历史还原、历史启发还是自创混合体系；这是考据要求，不替代成图风格。只有会影响当前道具的时代、地域、阶层和工艺信息才需确认，不预设整套文明史。

不要先要求用户填满所有配置。准备清单可先做；需要造型选择时再问决定性的缺口。风格未知可输出标注假设的探索方案，不将其锁成全剧定稿。

## P1 道具需求

### 读取与对照

1. 识别实际文件结构和道具表头，保留名称、ID及来源位置；不要求用户先转成固定 JSON。
2. 识别父资产/状态行，分别记录，不合并成没有状态关系的长描述。
3. 两者都有时以清单为入口查剧本，提取剧情作用、操作者、动作、状态触发与明确外观。只有表时按表设计，不编造剧情；只有剧本时先建立有依据的道具工作清单。定位用实际表行或集/场，只有验证过才能写页码。
4. 区分画面出现、台词提及、连续性延续；文本片段或词匹配不能当作整剧覆盖证明。
5. 将资料冲突、别名身份不明、表外物件单列。未找到证据的表内条目保留并说明，不自动删除。

### 提炼设计要求

从动作推导需要表达的结构，不借动作编造材质或机构。例如“打开并取出物件”说明需要开合和容纳关系，但不自动规定合页类型、锁扣、木材或精确尺寸。

把需求拆成三层：

- 必须满足：用户明确要求、剧情功能、来源明确的外观限制。
- 应设计补全：轮廓、部件关系、尺度、材质/配色、识别符号和必要交互。
- 可选增强：不改变身份与剧情的装饰、磨损和展示效果。

规划所需视角/状态。逐件阶段模式不立即为全部项目写词；用户要求整张Prompt表时，按批量表规则连续完成清单内设计与写词。按叙事重要性、使用频率、交互复杂度和用户优先级建议设计深度；不虚构已定镜头或强制每项英雄级。

### 品类路由

- 硬表面/武器/器具：优先部件、轮廓、握持与使用关系。
- 软质物件：优先形状、折叠/抓握、纹样与变形一致性。
- 佩饰/发饰：单体与角色佩戴共享同一造型；核对角色既有配饰，不重复设计。
- 物质+容器：区分内容物和载体，明确锁定层与变化层；不自动拆新 ID。
- 纸面资产：先确认是否需可读内容；版式与正文分别处理，不编造信件或契约内容。
- 植物/坐骑/效果：保留清单身份，采用适合的视觉审核与交付，不机械套硬表面工程检查。

魔法能力是可与上述品类叠加的设计层，不把神器全部归为武器。涉及能力、活体或变形时，按 [神话与魔法道具专项](myth-and-magic-props.md) 补充有依据的触发、状态和身份保持要求；剧情未规定的能力、代价或状态只能作为提案，不能自动写成正式设定。

## P2 概念方向

将需求转成有实质区别的方案。区别应落在轮廓、功能结构、材质组合或造型语言，而不只是换颜色。

每个方向说清：设计概念、关键轮廓与部件、材质/配色、世界观识别、交互适配、主要取舍。控制方案数量，足以支持选择即可，不固定要求三案或穷举全部组合。

说明哪些遵循来源、哪些是提案。推荐一案并给出理由，但推荐不是用户确认。逐件阶段模式中，用户选定或明确授权后登记方向版本，再进入P3；批量Prompt表模式可直接将推荐提案写入表和完整词，不登记为用户已选定。

若用户要求只写方向，不进一步生成主视觉词。若用户已提供选定方向，核对约束后直接使用，不重新选型。

## P3 主视觉提示词

道具资产图默认采用 [固定结构提示词](prompt-table.md#固定结构提示词)：同一张图内正面、侧面、背面＋一个局部细节特写，白色或浅灰色背景。三视图保持同一状态、主体尺度、造型和部件关系；未给出的背面细节作为设计补全，不冒充已有依据。展示图不冒充精确正交工程图。用户另行要求单体主视觉时，再按形态选择适合的单一观察角度。

提示词组织顺序：固定三视图正文 → 道具具体设计 → 一个特写部位 → 项目视觉风格 → 排版、一致性与排除项。用户另行指定图类型时保留设计内容，调整目标与展示条款，不塞入相互矛盾的单视图要求。

- 用可见描述替代只有气氛的词。关键设定在完整提示词里自足，不只写“沿用上面的方案”。
- 参考图逐张声明用途：造型、风格、角色尺度或目标状态；不要笼统“完全参考所有图”。
- 基础资产图避免遮挡关键结构，使用白色或浅灰色干净背景；画幅和分辨率只有用户或下游明确要求时固定。
- 有可读文字时使用已确认文本；如工具不能可靠保持字形，交付时安排单独排字和文字校核，不承诺生成已正确。
- 不指定用户未选择的模型参数、固定分辨率或某截图中的工具。

输出完整提示词后完成本轮写词任务；用户要求继续图片制作时再等待回流。批量表不为等待一件道具的图而停止其他行的写词。此阶段最多说明提示词已准备，不说资产已生成、已通过或已定稿。

## P4 回流审核与主视觉锁定

先确认图片实际可查看、对应哪个道具/方向/版本。附件不清楚或部分不可见时说明限度，只评估可见部分。

审核顺序：

1. 剧情与明确要求：道具身份、功能表达、必要交互和限定外观。
2. 结构表达：关键部件数量/位置、连接、比例、握持或开合是否在视觉上合理。
3. 视觉一致性：轮廓、固有色/材质、符号与已选方向。
4. 资产可用性：遮挡、背景分离、必要信息是否足够，是否满足当前下游用途。

三视图资产图额外核对：三个方向齐全且不同，特写只有一个且与主体对应；造型、颜色、材质、比例、部件数量、状态和柔性摆放没有跨视图漂移。未回流图片前不能把这些检查项记为已经通过。

不要把概念图审核说成实物强度、精确尺寸或制造验证。

### 分支处理

- 有阻断问题：说明问题与证据，回到方向调整或局部修图；不锁成无问题基准。
- 局部问题：给有边界的修图包，保持主体不变；收到新图后再审核。
- 只有审美建议：交给用户选择，不能用个人偏好强制返工。
- 可用于锁定：告知检查结果，等待用户确认具体图。
- 用户选择仍有问题的图：明确列出问题与接受的取舍；不自动视为已接受所有缺陷。确认其处理方式后可登记带例外基准。

只有用户确认后，登记主视觉文件、版本和身份不变量。不能从“这张不错”推断用户要求同时锁定其他道具或派生图。

## P5 视角、状态与交互扩展

依据 P1 的规划和当前下游要求形成最小扩展清单，逐项明确目的：

- 视角：解决某个可见面或结构信息缺口；正交图与透视展示分别标记。
- 状态：开合、启动、污渍、破损等，须有剧情或用户依据。
- 交互：佩戴、持握、携带、递交等，通常是构图/使用示意，不自动新建状态 ID。

主视觉已锁定后才派生；用户提供已有定稿可直接作为候选基准核对。每个提示词列出“必须保持”和“允许改变”，并指明基准版本。

上述锁定条件适用于正式图像派生。仅交批量Prompt表时，上游明确的状态可先写继承同一文字设计的草案，按 `prompt-table.md` 标待锁图核对；不得把文字继承说成实际图片一致性已通过。

### 派生规则

- 先补清必要的不可见结构，再出依赖它的视角或开合图；补全属于设计，不是原图事实。
- 常规状态以同一基础结构变化。破损需能与完整部件对应，发光不替换材质分区，血污不成为永久新配色。明确要求变形时，先确认形态关系、允许改变的结构及跨形态身份线索，再按 [神话与魔法道具专项](myth-and-magic-props.md) 核查，不把所有结构变化都视为身份漂移。
- 角色参考锁角色身份/姿态/尺度，主视觉参考锁道具；二者冲突要说明，不用角色图无声重设计道具。
- 每一张回流都与指定基准核对。审核通过与用户选择分别记录，不从一张成功推定整组成功。
- 当前派生失败，优先返工该项。只有基准自身必须调整时才改版，并列出需要重核的派生项。

无需穷举全部侧面、背面、俯视或状态。用户要求扩展方案而非出图时，只交付清单与顺序。

## P6 审核与交付

根据约定范围核查：

- 基础资产与原 ID 对应，已确认主视觉及版本可定位。
- 所需视角、状态、交互示意实际存在，关联正确基准。
- 提示词、参考图职责、审核结果和用户选择可追溯。
- 未完成项、已接受差异和使用限制清楚，不用“全流程完成”遮蔽缺图。
- 下游所需内容实际满足；无明确3D要求时不强制 PSD、PBR、六视图或制造图。

交付索引优先列实际文件，不把计划文件列成现存产物。用户只要求提示词或某阶段时，可以结束该阶段，标明后续待回流，不宣称整个资产完工。

## 批量任务与调度

- 初始整理：先汇总设计范围、全局风格和道具准备清单；用户要求整表时继续写清单内的设计与完整Prompt，不停在准备清单。其他阶段模式再按用户指定或建议优先级进入单体设计。
- 共享与独立：项目风格、阵营符号和尺度体系可以共享；不同道具的造型基准和状态审核不能互相代替。同一套件的关联关系需明确记录。
- 分批交付：按用户范围及可审查规模分批，交付本批的方向或提示词，不淹没用户于全部阶段的混合产物。
- 独立等待：部分资产待方向选择或图片回流时，其他已具备依据且在授权范围内的资产可继续。逐件确认模式不能自动采纳未选方案；批量Prompt表可以写推荐草案，但不得记为已确认。
- 回流匹配：按原资产、方向/基准版本、目标视角/状态分配图片。文件名不明或一组图身份不清时先核对，不强行挂到当前资产。
- 汇总进度：区分准备完成、提示词完成、待回流、已锁基准、派生待审核和交付完成；不得只用一个全局“完成”覆盖各条目。

用户未授权扩大到下一批时，交付当前批次并说明可继续项。已授权全表推进时，不反复要求同一范围授权，但方向/选图等设计确认仍按用户约定执行。

## 续做和改版

恢复任务先读取最近进度、当前基准和待办，不凭对话印象覆盖已选方向。没有持久记录时先用现有附件和明确确认恢复必要信息。

- 修改剧情/需求：回 P1，检查对方向、基准与派生的影响。
- 修改设计方向：回 P2，保留旧选择，重新走主视觉确认。
- 更换主视觉：回 P4，登记新版本，受影响派生标“需重核”。
- 只修改某状态/角度：留在 P5，不重启其他资产。

每轮指出当前节点和最小下一输入；只有需要用户选择或图片回流时等待，不以“全流程”推定可越过确认。
