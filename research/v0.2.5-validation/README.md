## 证据判断

检查是否综合各场证据而不是采信一个人物标签；是否补出可画的外观留白并区分事实/推导/创作；条件改变是否只影响合理部位；独立专项是否有真实调用和返回，而非仅在成稿写名称。结果按具体证据记录通过、缺陷与未执行，不使用主观总分。

全文理解缓存、候选转正、阶段失效和旧项目兼容由确定性回归测试验证；真实文字验收只能证明此次调用的设计行为，不等于图像一致性或全剧大规模质量保证。

## C：原生独立会诊与总控整合

复杂结构案例在 Desktop 原生 Codex 宿主完成文字验收：总控先形成共享人物简报和两个任务，再由两个独立子代理分别实际读取剪裁／饰品 Skill 与知识，未读取彼此结果，各自提交 V1.2 真实提案；原始输入和返回见 [native-C](native-C/)。两个返回物均通过实际合同校验，SHA、采用和驳回原因见 [integration.json](native-C/integration.json)。本案例的独立会诊数为 **2**，没有执行人类批准轮次。

两专项确实产生需要总控处理的冲突：剪裁方案留 `65×12mm` 横向净区，饰品方案要 `12×30mm` 竖条。总控采纳窄竖条，调整衣片净区为约 `16×34mm`，统一为软织物四边平缝、哑光织字，并要求落在门襟与安全带之间可用区域。衣领、肩缝、腋下活动片和内掖下摆共同服务狭舱、阀门动作及安全带，不增加人物身世或重做身份。

这证明此次原生宿主中的真实专项参与和具体整合裁决，**不代表 App Server 自主派生了子代理**。设计仍未批准；安全带空窗需实装测量，样衣动作、湿态可读性及图片均未验证。详见 [整合稿](native-C/integration.md)。

## 正式模板与独立草稿

保留原始 [design-basis.json](final-short/design-basis.json) 是为了可复核真实模型行为；其中 `schema_version` 的文字标签本身不等于通过正式合同校验。独立分析可用草稿标签和自由结构承载推荐，建立项目后须按正式模板重新绑定来源单位、标准角色 ID、字段类型及阶段父引用，并通过 submit 校验。当前三个文件都不构成审批记录，也没有被用来推进正式资产链。

正式来源防伪和阶段作用域测试使用确定性材料检查约束；其中合成状态文件不是真实图片，测试中的人工批准是状态机测试输入，不是用户批准。精确结构见[最小身份合同与三个 JSON 样例](../../character-assets/examples/phased-identity-contract.md)。
